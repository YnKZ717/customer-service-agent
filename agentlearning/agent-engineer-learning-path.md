# Agent 工程师系统学习路径

> 目标：从"会用 LLM"到"能独立设计企业级 Agent 系统"
> 适用对象：有 LLM 调用经验，但缺乏 Agent 工程体系认知的开发者
> 日期：2026-08-21

---

## 前言：你为什么需要这套学习路径

你现在的认知瓶颈不在技术，在于没有"框架"。

"LLM 插上了手脚"这个描述说明你把 Agent 看成 LLM 的功能扩展，而不是一个独立的工程范式。实际上 Agent 和 LLM 的关系，就像"操作系统"和"CPU"的关系——CPU 是计算核心，但操作系统的价值在于进程调度、内存管理、文件系统这些围绕 CPU 构建的工程体系。LLM 是推理引擎，Agent 的价值在于推理引擎之上的那一整套工程：**状态机、记忆层、工具编排、任务规划、多智能体协作、人机交接协议**。这些东西 LLM 本身不提供，是你作为工程师要去设计的。

你三个阶段的问题本质上是同一个：**一直在"用"，没有在"设计"**。写 skills 是调 API，搭客服 Agent 是拼组件，但从来没有从"如果我要为一家企业从零设计一个 Agent 系统，我需要先搞清楚什么"这个角度思考过。

这份文档的目标不是教你写代码，而是帮你建立 Agent 工程师的认知框架。

## 第一部分：Agent 基础理论

### 1.1 什么是 Agent？——与 Chatbot、LLM 的本质区别

| 维度 | Chatbot | LLM | Agent |
|------|---------|-----|-------|
| 核心能力 | 模式匹配/检索 | 文本生成/推理 | 自主规划 + 执行 + 反馈 |
| 状态 | 无状态（每轮独立） | 无状态（上下文窗口内） | 有状态（跨轮次记忆） |
| 行动 | 只能回复文本 | 只能输出 token | 能调用工具、改变外部世界 |
| 决策 | 固定流程树 | 概率生成 | 基于目标的动态规划 |
| 反馈循环 | 无 | 无 | 有（观察结果→调整策略） |

**关键认知：Agent = LLM（推理引擎）+ 状态机（记忆与流程）+ 工具层（行动能力）+ 规划器（决策逻辑）**

LLM 只是 Agent 的"大脑"。一个没有状态管理、没有工具调用、没有规划能力的 LLM 应用，不管包装得多好看，本质上还是一个 chatbot。

### 1.2 Agent 的三种架构范式

#### 范式一：ReAct（Reasoning + Acting）
- **核心思想：** 思考→行动→观察→思考→行动... 循环
- **流程：** LLM 生成 thought → 选择 action → 执行 tool → 观察 observation → 继续思考
- **优点：** 简单直观，可解释性强（每一步 thought 都可见）
- **缺点：** 每步都要调用 LLM，token 消耗大；复杂任务容易迷失
- **适用场景：** 单步决策明确的任务（搜索、问答、简单工具调用）
- **代表框架：** LangChain ReAct Agent

#### 范式二：Plan-and-Execute（规划后执行）
- **核心思想：** 先制定完整计划，再逐步执行
- **流程：** LLM 生成 plan（步骤列表）→ 逐步骤执行 → 每步可 re-plan
- **优点：** 全局视野好，不会在复杂任务中迷失
- **缺点：** 初始规划可能不准，需要 re-plan 机制
- **适用场景：** 多步骤复杂任务（代码生成、数据分析、工作流编排）
- **代表框架：** LangGraph、AutoGen

#### 范式三：Reflection / Self-Refinement（反思式）
- **核心思想：** 生成→评估→修正循环
- **流程：** LLM 生成初稿 → 评估器（可以是另一个 LLM）打分 → 根据反馈修正 → 再评估
- **优点：** 输出质量高，适合需要精确性的任务
- **缺点：** 多次调用 LLM，延迟高
- **适用场景：** 代码审查、文案润色、翻译质量提升
- **代表框架：** Reflexion、Critic Agent

**你的客服 Agent 属于哪种？**
- 排查流程 → Plan-and-Execute（有预定义的决策树）
- FAQ 问答 → ReAct（单步决策：查知识库→返回答案）
- 回答评估 → Reflection（副 Agent 评估主 Agent 回答）
- **你实际上已经在用三种范式了，只是没有意识到**

### 1.3 Agent 的核心循环（The Agent Loop）

所有 Agent 架构都共享一个基本循环：

```
┌─────────────────────────────────────────┐
│                  LOOP                    │
│                                          │
│  1. 感知（Perceive）                      │
│     接收用户输入 + 环境状态 + 历史记忆      │
│         ↓                                │
│  2. 推理（Reason）                         │
│     LLM 分析当前状态，决定下一步行动         │
│         ↓                                │
│  3. 行动（Act）                            │
│     调用工具 / 查询知识库 / 调用其他 Agent   │
│         ↓                                │
│  4. 观察（Observe）                        │
│     收集行动结果，更新内部状态               │
│         ↓                                │
│  5. 判断（Decide）                         │
│     任务完成了吗？需要继续吗？               │
│     ├── 完成 → 输出结果                    │
│     └── 继续 → 回到第 1 步                 │
│                                          │
└─────────────────────────────────────────┘
```

**工程师视角：** 你设计 Agent 时，实际上是在设计这个循环的每个环节：
- 感知环节 → 定义输入格式、状态结构
- 推理环节 → 选择 LLM、设计 prompt、决定推理策略
- 行动环节 → 定义工具集、工具调用协议
- 观察环节 → 定义结果解析、错误处理
- 判断环节 → 定义终止条件、最大步数、降级策略

## 第二部分：Agent 工程核心模块

### 2.1 状态管理（State Management）

**为什么状态管理是 Agent 工程的第一优先级？**

Chatbot 不需要状态（每轮对话独立），但 Agent 必须有状态。状态决定了 Agent "记得什么"、"正在做什么"、"下一步能做什么"。

**状态管理的核心挑战：**

| 挑战 | 说明 | 你的项目中的体现 |
|------|------|-----------------|
| 状态膨胀 | 对话越长，状态越大，LLM 上下文窗口有限 | history 截断到最近 8 轮 |
| 状态一致性 | 多轮对话中状态可能不同步 | troubleshoot_flow 在排查结束后没有清空 |
| 状态恢复 | 断线/重启后如何恢复状态 | 从 history 中解析"故障排查中"标记 |
| 状态共享 | 多 Agent 间如何共享状态 | 你的项目是单 Agent，暂不涉及 |

**工程师要掌握的模式：**
- **黑板式（Blackboard）：** 所有 Agent 共享一个全局状态板，各自读写（适合多 Agent 协作）
- **消息传递式（Message Passing）：** Agent 之间通过消息通信，不共享状态（适合分布式系统）
- **分层式（Hierarchical）：** 主 Agent 管理全局状态，子 Agent 管理局部状态（适合复杂任务分解）

### 2.2 记忆系统（Memory System）

Agent 的记忆分为三层：

| 层次 | 内容 | 典型实现 |
|------|------|---------|
| 短期记忆（Working Memory） | 当前对话上下文、当前任务状态、最近 N 轮对话历史 | 对话历史列表 |
| 中期记忆（Episodic Memory） | 本次会话的关键事件、用户已提供的信息、已执行的操作记录 | user_memory dict |
| 长期记忆（Semantic Memory） | 用户画像/偏好、领域知识库、历史经验/教训 | 向量数据库 + FAQ |

**工程师要掌握的技术：**
- **向量数据库：** 长期记忆的存储和检索（Milvus、Pinecone、Chroma）
- **记忆压缩：** 对话历史过长时如何摘要压缩（Map-Reduce 摘要、滑动窗口）
- **记忆检索：** 如何从海量记忆中精准找到相关信息（RAG、HyDE、Query Decomposition）
- **记忆遗忘：** 哪些记忆该保留、哪些该过期删除（TTL、重要性评分）

### 2.3 工具层（Tool Layer）

工具是 Agent 的"手脚"。没有工具，Agent 只能"说"不能"做"。

**工具编排的核心问题：**

| 问题 | 说明 |
|------|------|
| 工具选择 | LLM 如何从多个工具中选出正确的？ |
| 参数提取 | LLM 如何从用户输入中提取工具参数？ |
| 错误处理 | 工具调用失败怎么办？重试？降级？ |
| 结果注入 | 工具返回结果如何喂回 LLM？ |
| 权限控制 | 哪些工具 Agent 可以自主调用，哪些需要人工确认？ |

### 2.4 规划器（Planner）

**三种规划策略：**

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| 预定义流程（Scripted） | 决策树/流程图，固定路径 | 客服排查、审批流程 |
| LLM 动态规划（LLM-planned） | LLM 实时生成执行计划 | 开放域任务、创意工作 |
| 混合式（Hybrid） | 预定义框架 + LLM 填充细节 | 大部分企业场景 |

### 2.5 评估器（Evaluator）

评估维度：准确性（回答是否正确）、相关性（是否切题）、安全性（有无敏感信息泄露）、完整性（有无遗漏）、语气/风格（是否符合品牌调性）。

## 第三部分：多 Agent 系统

### 3.1 为什么需要多 Agent？

单 Agent 的局限：
- **上下文窗口限制：** 一个 LLM 装不下所有知识
- **专业分工：** 不同任务需要不同的 prompt/工具/模型
- **可靠性：** 单点故障风险，需要冗余和校验
- **复杂性管理：** 一个超级 prompt 比一组小 prompt 更难维护

### 3.2 多 Agent 协作模式

#### 模式一：主从式（Orchestrator-Worker）
主 Agent 接收用户输入、分解任务，分发给 Worker Agent 各自执行，最后汇总结果。适合任务可分解为独立子任务的场景。你的项目中的主 Agent + 副 Agent 评估就是简化的主从式。

#### 模式二：流水线式（Pipeline）
Agent A（意图识别）→ Agent B（知识检索）→ Agent C（回答生成）→ Agent D（安全审查）→ 输出。任务有明确的先后顺序。你的 classify → kb_answer → chunk_search → general → evaluate 就是流水线。

#### 模式三：辩论式（Debate / Adversarial）
Agent A 生成答案 → Agent B 挑毛病 → Agent A 修正 → ... → 收敛。适合需要高质量输出的场景（代码审查、法律分析）。需要设定终止条件（最大轮数/共识阈值）。

#### 模式四：共享黑板式（Blackboard）
所有 Agent 共享一个全局状态板，各自贡献自己的专业判断。适合多专家协作（医疗诊断、金融分析）。

### 3.3 Agent 间通信协议

| 协议 | 说明 | 优劣 |
|------|------|------|
| 消息传递 | Agent 之间发送结构化消息 | 灵活但需要定义消息格式 |
| 共享状态 | 所有 Agent 读写同一个 State | 简单但可能冲突 |
| 事件驱动 | Agent 发布/订阅事件 | 解耦但调试困难 |

## 第四部分：Agent 企业垂直化

### 4.1 RAG（检索增强生成）

RAG 是企业 Agent 的核心基础设施。没有 RAG，Agent 只能靠 LLM 的预训练知识，无法了解企业私有数据。

**完整流程：** 用户问题 → Query 改写 → 向量检索 → 重排序 → 注入 Prompt → LLM 生成 → 后处理

| 环节 | 关键决策 | 常见选择 |
|------|---------|---------|
| Query 改写 | 是否改写用户原始问题？ | HyDE、Query Decomposition、Multi-Query |
| 向量化 | 用什么 embedding 模型？ | OpenAI text-embedding-3、BGE、M3E |
| 存储 | 用什么向量数据库？ | Milvus、Qdrant、Chroma、PgVector |
| 检索 | 用什么检索策略？ | Dense、Sparse（BM25）、Hybrid |
| 重排序 | 是否需要 rerank？ | Cohere Rerank、BGE-Reranker |
| 注入 | 怎么把检索结果放进 prompt？ | 模板、动态裁剪、压缩 |

### 4.2 领域适配

企业 Agent 需要"懂行"。领域适配的三个层次：
1. **知识层：** 注入领域知识库（FAQ、文档、数据库）
2. **行为层：** 定义领域特定的工作流（审批、排查、报告）
3. **语言层：** 调整语气、术语、回复风格（正式/友好/技术化）

### 4.3 安全与合规

| 风险 | 防御措施 |
|------|---------|
| Prompt 注入 | 输入过滤、输出审查、系统 prompt 隔离 |
| 数据泄露 | 敏感信息脱敏、工具权限分级、审计日志 |
| 幻觉 | 事实核查、引用来源、置信度阈值 |
| 滥用 | 速率限制、内容审核、人工兜底 |

### 4.4 部署与运维

Agent 系统的运维特殊性：
- LLM 调用有延迟（需要流式输出）
- LLM 会失败（需要降级策略）
- LLM 输出不稳定（需要评估和监控）
- Token 有成本（需要用量监控和优化）
